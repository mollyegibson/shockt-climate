# Effect Style Guidance

## 1. Use Effect.fn for functions returning Effects

### Do This

```typescript
const listTasks = Effect.fn(function* (
  where: typeof TaskModelWhereSchema.Type,
  pagination: typeof PaginationSchema.Type,
  orderBy: typeof TaskModelOrderBySchema.Type
) {
  const tasks = yield* Effect.tryPromise(() =>
    db.query.tasks.findMany({
      ...pagination,
      where: whereForTaskWhere(where),
      orderBy: orderByForTask(orderBy)
    })
  );
  const tasksWithEmptyMessages = tasks.map((task) => ({ ...task, messages: [] }));
  const decodedTasks = yield* decodeArray(TaskModel)(tasksWithEmptyMessages);
  return decodedTasks;
});
```

### Don't Do This

```typescript
const listTasks = (
  where: typeof TaskModelWhereSchema.Type,
  pagination: typeof PaginationSchema.Type,
  orderBy: typeof TaskModelOrderBySchema.Type
) =>
  Effect.gen(function* () {
    const tasks = yield* Effect.tryPromise(() =>
      db.query.tasks.findMany({
        ...pagination,
        where: whereForTaskWhere(where),
        orderBy: orderByForTask(orderBy)
      })
    );
    const tasksWithEmptyMessages = tasks.map((task) => ({ ...task, messages: [] }));
    const decodedTasks = yield* decodeArray(TaskModel)(tasksWithEmptyMessages);
    return decodedTasks;
  });
```

## 2. Prefer generator syntax over pipe

### Do This

```typescript
const listTasks = Effect.fn(function* (
  where: typeof TaskModelWhereSchema.Type,
  pagination: typeof PaginationSchema.Type,
  orderBy: typeof TaskModelOrderBySchema.Type
) {
  const tasks = yield* Effect.tryPromise(() =>
    db.query.tasks.findMany({
      ...pagination,
      where: whereForTaskWhere(where),
      orderBy: orderByForTask(orderBy)
    })
  );
  const tasksWithEmptyMessages = tasks.map((task) => ({ ...task, messages: [] }));
  const decodedTasks = yield* decodeArray(TaskModel)(tasksWithEmptyMessages);
  return decodedTasks;
});
```

### Don't Do This

```typescript
const listTasks = Effect.fn(function* (
  where: typeof TaskModelWhereSchema.Type,
  pagination: typeof PaginationSchema.Type,
  orderBy: typeof TaskModelOrderBySchema.Type
) {
  return yield* Effect.tryPromise(() =>
    db.query.tasks.findMany({
      ...pagination,
      where: whereForTaskWhere(where),
      orderBy: orderByForTask(orderBy)
    })
  ).pipe(
    Effect.map((tasks) => tasks.map((task) => ({ ...task, messages: [] }))),
    Effect.flatMap(decodeArray(TaskModel))
  );
});
```

### Exception: Pass combinators to Effect.fn

```typescript
const listTasks = Effect.fn('TaskRepo.listTasks')(
  function* (params: typeof TaskListParamsSchema.Type) {
    const tasks = yield* Drizzle.use((db) =>
      db.query.tasks.findMany({
        ...params.pagination,
        where: whereForTaskWhere(params.where ?? {}),
        orderBy: orderByForTask(params.orderBy)
      })
    );
    const tasksWithEmptyMessages = tasks.map((task) => ({ ...task, messages: [] }));
    const decodedTasks = yield* decodeArray(TaskModel)(tasksWithEmptyMessages);
    return decodedTasks;
  },
  Effect.sandbox,
  Effect.mapError(InfrastructureError.fromCause('Error listing tasks'))
);
```

### Exception: Use .pipe() for simple effects

```typescript
const assignSkill = Effect.fn('AgentRepo.assignSkill')((params: typeof AgentSkillCreateSchema.Type) =>
  Effect.tryPromise(() =>
    db
      .insert(agentSkills)
      .values([params])
      .onConflictDoNothing({ target: [agentSkills.agentId, agentSkills.skillId] })
      .returning()
  ).pipe(Effect.sandbox, Effect.mapError(InfrastructureError.fromCause('Error assigning skill to agent')))
);
```

## 3. Prefer Effect.tryPromise over Effect.promise

### Do This

```typescript
Effect.tryPromise(() => db.query.tasks.findFirst());
```

```typescript
Effect.tryPromise({
  try: () => db.query.tasks.findFirst(),
  catch: (e) => new DbError(e)
});
```

### Don't Do This

```typescript
Effect.promise(() => db.query.tasks.findFirst());
```

## 4. Use the strictest Schema type possible

Always prefer the most constrained schema type that accurately models the data. This catches bugs at the boundary (API responses, DB reads, user input) rather than deep in business logic.

### Numeric types — match the actual domain

```typescript
// IDs generated by the database (starts at 1)
id: Schema.Int.pipe(Schema.positive())

// IDs that could be 0 (e.g. external system, zero-based index)
id: Schema.NonNegativeInt

// A count or quantity that cannot be negative
count: Schema.NonNegativeInt

// A percentage between 0 and 100
// Use Schema.Number.pipe(Schema.between(0, 100)) — not plain Schema.Number
percentage: Schema.Number.pipe(Schema.between(0, 100))

// Never use Schema.Number for a value you know must be a whole number
// Bad:
id: Schema.Number
// Good:
id: Schema.Int.pipe(Schema.positive())
```

### String types — be explicit about emptiness and structure

```typescript
// Any string that must not be empty
name: Schema.NonEmptyString

// A UUID field — use Schema.UUID, not Schema.String
id: Schema.UUID

// An email address
email: Schema.String.pipe(Schema.pattern(/^[^\s@]+@[^\s@]+\.[^\s@]+$/))

// A fixed set of values — use Schema.Literal, not Schema.String
status: Schema.Literal('active', 'inactive', 'pending')

// Never use Schema.String when the value is constrained
// Bad:
status: Schema.String
// Good:
status: Schema.Literal('active', 'inactive', 'pending')
```

### Nullable and optional fields — only where truly needed

Only reach for `Schema.NullOr`, `Schema.UndefinedOr`, `Schema.OptionFromNullOr`, or `Schema.optional` when the field is genuinely nullable/optional in the data source (database column, API response). Do not use them defensively.

```typescript
// A field that is always present — no wrapping needed
name: Schema.NonEmptyString

// A field the database may return as NULL
deletedAt: Schema.NullOr(Schema.String)

// An optional field in a request payload (may be absent)
description: Schema.optional(Schema.NonEmptyString)

// Never use NullOr/optional "just in case"
// Bad:
name: Schema.NullOr(Schema.String)  // if name is always present
// Good:
name: Schema.NonEmptyString
```

### Arrays — constrain length where meaningful

```typescript
// A list that must have at least one item
tags: Schema.Array(Schema.NonEmptyString).pipe(Schema.minItems(1))

// A bounded list
items: Schema.Array(Schema.Int.pipe(Schema.positive())).pipe(Schema.maxItems(100))
```

### Secret fields — use Schema.Redacted

When a schema decodes a field that must never reach a log line (an access token, an API key returned by a token-exchange response), wrap it in `Schema.Redacted` at the schema itself rather than relying on every caller to remember to wrap the decoded value.

```typescript
// Bad — plain string; a caller who forgets to Redacted.make it can log it by accident
const ExchangeResponseSchema = Schema.Struct({
  access_token: Schema.String,
  expires_in: Schema.NonNegativeInt
})

// Good — redacted at the boundary; every consumer gets a Redacted.Redacted<string>
const ExchangeResponseSchema = Schema.Struct({
  access_token: Schema.Redacted(Schema.String),
  expires_in: Schema.NonNegativeInt
})
```

A schema-level `Redacted` also means a downstream service that just forwards the value (`Option.some(result.access_token)`) never needs its own `Redacted.make(...)` call — the type already carries the guarantee.

### Avoid Schema.Any and Schema.Unknown at boundaries

`Schema.Any` and `Schema.Unknown` opt out of all validation. Only use them in truly dynamic contexts (e.g. plugin-provided data you cannot type ahead of time), and document why.

```typescript
// Bad — loses all type safety at the boundary
metadata: Schema.Any

// Better — use a defined structure, or at least a record type
metadata: Schema.Record({ key: Schema.String, value: Schema.Unknown })
```

## 5. Use Schema.make() for constructing schema-typed objects

When constructing objects that match a defined Schema, use `Schema.make()` instead of raw JavaScript objects with `as const` assertions. This applies to both production code and tests.

### Do This

```typescript
const payload = AgentExportSchema.make({
  version: '1.0',
  exportedAt: new Date().toISOString(),
  exportedFrom: tenant.slug,
  exportedBy: principal.name,
  agent: {
    id: agent.id,
    name: agent.name,
    agentType: agent.agentType
  },
  skills: []
});
```

### Don't Do This

```typescript
const payload = {
  version: '1.0' as const,
  exportedAt: new Date().toISOString(),
  exportedFrom: tenant.slug,
  exportedBy: principal.name,
  agent: {
    id: agent.id,
    name: agent.name,
    agentType: agent.agentType as const
  },
  skills: []
};
```

### Benefits

- **Type safety** - The schema validates field types at construction time
- **Cleaner code** - No scattered `as const` assertions throughout objects
- **Runtime validation** - Schema.make() validates the data matches the schema
- **IDE support** - Better autocomplete and error highlighting

### When mapping arrays

Use `Schema.make()` inside `.map()` when transforming data into schema-typed arrays:

```typescript
const skills = fetchedSkills.map((skill) =>
  SkillExportSchema.make({
    version: '1.0',
    exportedAt: new Date().toISOString(),
    exportedFrom: tenant.slug,
    exportedBy: principal.name,
    skill: {
      id: skill.id,
      title: skill.title,
      content: skill.content
    }
  })
);
```


## 6. HTTP client error handling: always check status and use typed error classes

When implementing HTTP clients, **always inspect `response.status` before reading the body.** Skipping this check means 4xx/5xx responses are either silently returned as data or bubble up as generic errors with no useful context.

### Use typed error classes, not InfrastructureError

Map HTTP status codes to specific error types. This makes error handling at the call site precise and self-documenting:

| Status | Error class | Meaning |
|---|---|---|
| 401 | `UnauthenticatedError` | Not authenticated — session expired or missing |
| 403 | `UnauthorizedError` | Authenticated but not permitted |
| 404 | `NotFoundError` | Resource does not exist |
| 400 / 422 | `InvalidRequestError` | Bad input — caller must fix the request |
| 5xx | `DownstreamServiceError` | The dependency is broken or unavailable |

`DownstreamServiceError` is the right name for 5xx: it signals that a service *this code depends on* failed, without implying a specific status code (500, 502, 503, 504 all mean the same thing to the caller — the dependency is not working).

Define these error classes once in a shared errors module and import them everywhere; don't redefine them per client.

```typescript
// errors.ts
class InvalidRequestError extends Schema.TaggedError<InvalidRequestError>()(
  'InvalidRequestError',
  { status: Schema.Int, message: Schema.String }
) {}

class DownstreamServiceError extends Schema.TaggedError<DownstreamServiceError>()(
  'DownstreamServiceError',
  { status: Schema.Int, message: Schema.String }
) {}
```

### The required pattern

There are two distinct failure modes to handle — transport errors and HTTP errors — and they go in different places:

- **Transport errors** (`RequestError`, `ResponseError`) come from `@effect/platform`'s `HttpClient`. `RequestError` means the request never reached the server (DNS failure, timeout, connection refused). `ResponseError` means the connection succeeded but reading the body failed. These are caught via a `catchTags` combinator passed to `Effect.fn`, which wraps the entire function.
- **HTTP errors** (4xx/5xx) mean the server responded but signalled failure. These are handled inside the function body by inspecting `response.status` after `client.execute`.

```typescript
export const getItem = Effect.fn('MyDomainClient.getItem')(
  function* (config: IMyDomainConfig, token: Redacted.Redacted, id: string) {
    const client = yield* HttpClient.HttpClient
    const response = yield* client.execute(
      HttpClientRequest.get(`${config.baseUrl}/items/${id}`, {
        headers: { Authorization: `Bearer ${Redacted.value(token)}` }
      })
    )

    // Handle HTTP-level errors by inspecting the status code.
    // client.execute succeeds for ANY status — it does NOT throw on 4xx/5xx.
    if (response.status >= 400) {
      const ErrorBodySchema = Schema.Struct({ message: Schema.String })
      const message = yield* response.json.pipe(
        Effect.flatMap((body) => Schema.decodeUnknown(ErrorBodySchema)(body)),
        Effect.map((parsed) => parsed.message),
        Effect.orElse(() => response.text.pipe(Effect.map((t) => t.trim() || `HTTP ${response.status}`))),
        Effect.catchAll(() => Effect.succeed(`HTTP ${response.status}`))
      )
      if (response.status === 401) {
        return yield* Effect.fail(new UnauthenticatedError({ message }))
      }
      if (response.status === 403) {
        return yield* Effect.fail(new UnauthorizedError({ message }))
      }
      if (response.status === 404) {
        return yield* Effect.fail(new NotFoundError({ message }))
      }
      if (response.status < 500) {
        return yield* Effect.fail(new InvalidRequestError({ status: response.status, message }))
      }
      return yield* Effect.fail(new DownstreamServiceError({ status: response.status, message }))
    }

    return yield* response.json
  },
  // Transport-level errors: the request never completed or the body could not be read.
  // These wrap the entire function body and are unrelated to the HTTP status code.
  Effect.catchTags({
    RequestError: () =>
      Effect.fail(new DownstreamServiceError({ status: 0, message: 'Network error — could not reach MyApi' })),
    ResponseError: () =>
      Effect.fail(new DownstreamServiceError({ status: 0, message: 'Failed to read MyApi response body' }))
  })
)
```

### Extract the status mapper once a second client needs it

The status-to-error-class `if` chain above is the same five branches in every client. When a second client needs it, extract it into one shared `mapHttpStatusToError({ status, operation, detail })` helper rather than copying the chain. Keep an inline branch only for a status that needs a message with diagnostic content the shared helper can't know, and delegate every other status to the helper.

### Prefer Schema.decodeUnknownSync outside an Effect context

`Effect.runSync(Schema.decodeUnknown(schema)(value))` works, but a failed decode throws a `FiberFailure` — Effect's internal defect wrapper, not a plain `Error` with a clean `.message`. A `catch (err) { err instanceof Error ? err.message : ... }` at the call site silently falls through to the generic branch instead of surfacing the actual parse failure.

`Schema.decodeUnknownSync(schema)(value)` throws a `ParseError` directly — a real `Error` subtype with a readable message — and needs no `Effect.runSync` wrapper. Use it anywhere you're decoding synchronously outside an Effect generator (a plain `async function` in browser code, a non-Effect utility function):

```typescript
// Bad — throws an untyped FiberFailure on decode failure
const decoded = Effect.runSync(Schema.decodeUnknown(MySchema)(value))

// Good — throws a typed ParseError with a real message
const decoded = Schema.decodeUnknownSync(MySchema)(value)
```

This only applies outside an Effect generator. Inside `Effect.gen`, `yield* Schema.decodeUnknown(schema)(value)` is already correct — see §6's HTTP client pattern above.

### Anti-patterns to avoid

```typescript
// Bad — skips status check; 4xx body is silently returned as valid data
const response = yield* client.execute(request)
const json = yield* response.json
return json

// Bad — uses InfrastructureError as a catch-all; callers cannot distinguish
// auth failures from not-found from server outages
Effect.catchTags({
  RequestError: (e) => Effect.fail(InfrastructureError.make({ message: 'Error calling API', cause: Cause.fail(e) })),
  ResponseError: (e) => Effect.fail(InfrastructureError.make({ message: 'Error calling API', cause: Cause.fail(e) }))
})
```

## 7. Define domain errors with Schema.TaggedError

Use `Schema.TaggedError` for all expected (recoverable) domain errors. The `_tag` discriminant enables precise handling with `Effect.catchTag` and ensures errors are typed throughout the call stack.

```typescript
// Good — structured, schema-aware, discriminated
class AgentNotFoundError extends Schema.TaggedError<AgentNotFoundError>()(
  'AgentNotFoundError',
  { agentId: Schema.Int.pipe(Schema.positive()) }
) {}

class ValidationError extends Schema.TaggedError<ValidationError>()(
  'ValidationError',
  { message: Schema.NonEmptyString }
) {}
```

Never use plain `Error` subclasses or plain objects as typed errors — they cannot be tracked in the Effect error channel.

```typescript
// Bad — untyped, not tracked by Effect
throw new Error('Agent not found')
return Effect.fail(new Error('Agent not found'))
```

## 8. Distinguish expected errors from defects

Effect has two distinct failure modes:

- **Expected errors** (`Effect.fail`) — things that can legitimately happen: not found, auth failure, validation. These appear in the `E` type parameter and must be handled by callers.
- **Defects** (`Effect.die`) — programming bugs or truly unrecoverable conditions. These bypass the error channel and are not part of the function's contract.

Use `Effect.die` for invariant violations and unimplemented stubs — not for business logic failures.

```typescript
// Good — defect for a condition that should never occur
if (!config.apiKey) {
  yield* Effect.die(new Error('ApiKey missing from config — this is a bug'))
}

// Good — expected error for a normal business condition
if (!agent) {
  yield* Effect.fail(new AgentNotFoundError({ agentId }))
}
```

### Use Cause.fail — not Cause.die — when wrapping caught errors

When constructing a typed error that wraps another error (e.g. building the `cause` field of a `Schema.TaggedError`), always use `Cause.fail` for caught/expected errors and reserve `Cause.die` for true invariant violations.

```typescript
// Good — downstream HTTP 500 is an expected failure; wrap with Cause.fail
return yield* Effect.fail(
  DownstreamServiceError.make({
    message: `PRO API returned ${status}`,
    cause: Cause.fail(new Error(`HTTP ${status}`))
  })
)

// Bad — Cause.die inside Effect.fail marks a handled error as a defect.
// This causes the error to propagate as a defect through catchAllDefect
// rather than as a typed error through catchAll/catchTag, silently
// bypassing any error-channel handling in callers.
return yield* Effect.fail(
  DownstreamServiceError.make({
    message: `PRO API returned ${status}`,
    cause: Cause.die(new Error(`HTTP ${status}`))  // ← wrong
  })
)
```

**Why it matters:** `Cause.die` inside a `cause` field causes Effect's runtime to classify the logged error as a defect (you'll see `_tag: 'Die'` in logs). More importantly, if the error is ever re-raised or inspected by `catchAllDefect` / `tapDefect`, the inner defect will surface unexpectedly. The `cause` field on a typed error should reflect how *that error came to exist* — a caught HTTP failure is a `Cause.fail`, not a `Cause.die`.

### Handling errors: prefer catchTag over catchAll

`Effect.catchTag` handles a single named error precisely. `Effect.catchAll` handles all expected errors at once — use it only at boundaries where you genuinely need to collapse all errors into one type.

```typescript
// Good — targeted recovery
yield* fetchAgent(id).pipe(
  Effect.catchTag('AgentNotFoundError', () => Effect.succeed(defaultAgent))
)

// Only use catchAll when you need to handle every error uniformly
yield* program.pipe(
  Effect.catchAll((error) => Effect.logError('Unhandled error', error))
)
```

`catchAllDefect` and `catchAllCause` swallow defects — only use them at the outermost application boundary (e.g. HTTP request handler), never in domain or library code.

## 9. Define services with Effect.Service

Use `Effect.Service` to define services. This co-locates the `Context.Tag` and `Layer` in one declaration and eliminates the boilerplate of defining them separately.

```typescript
// Good
class AgentRepository extends Effect.Service<AgentRepository>()(
  'AgentRepository',
  {
    effect: Effect.gen(function* () {
      const db = yield* Database
      return {
        findById: Effect.fn(function* (id: number) {
          // ...
        })
      }
    }),
    dependencies: [Database.Default]
  }
) {}

// Use AgentRepository.Default to provide the layer
// Use yield* AgentRepository to access the service in effects
```

Add `accessors: true` when you want module-level accessor functions generated automatically (useful for frequently-used services).

## 10. Add human-readable messages to Schema constraints

When adding validation constraints to a schema field, include a `message` so that parse errors are actionable rather than generic.

```typescript
// Good — error message tells you what went wrong
const PasswordSchema = Schema.NonEmptyString.pipe(
  Schema.minLength(8, { message: () => 'Password must be at least 8 characters' }),
  Schema.maxLength(128, { message: () => 'Password must be at most 128 characters' })
)

// Bad — generic Effect parse error with no context
const PasswordSchema = Schema.String.pipe(
  Schema.minLength(8),
  Schema.maxLength(128)
)
```

## 11. Use branded types for domain IDs

When multiple ID types share the same primitive type (e.g. `number` or `string`), use `Schema.brand` to make them nominally distinct. This prevents accidentally passing an `AgentId` where a `TaskId` is expected.

```typescript
// Good — AgentId and TaskId are distinct types at compile time
const AgentId = Schema.Int.pipe(Schema.positive(), Schema.brand('AgentId'))
const TaskId  = Schema.Int.pipe(Schema.positive(), Schema.brand('TaskId'))
type AgentId  = Schema.Schema.Type<typeof AgentId>
type TaskId   = Schema.Schema.Type<typeof TaskId>

// TypeScript will reject this:
const getTask = (id: TaskId) => { ... }
getTask(agentId) // Error: Argument of type 'AgentId' is not assignable to 'TaskId'
```

Use `Schema.brand` at the schema definition layer so that decoding automatically produces the branded type — no manual casting required.
